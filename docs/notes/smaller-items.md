### Item 13: the slow server tests

Each test uses a local server that accepts the connection and never answers. The limit is a setting that the test makes short. The test checks that the call ends near the limit, with a message that names the limit and the next step, and that nothing stays behind.

| Call | Limit (default) | Test |
|---|---|---|
| Hub, `git fetch` and `git ls-remote` | 120 s (`SourceConfig::git_timeout`) | `git_gives_up_on_a_server_that_never_answers`, `the_hub_gives_a_git_install_a_clear_error_when_the_server_is_silent` |
| Hub, JSON from a directory or a marketplace | 20 s (`http_timeout`) | `http_gives_up_on_a_directory_and_a_download_that_never_answer` |
| Hub, archive and npm downloads | 120 s (`download_timeout`) | the same test |
| Hub, Composio | 90 s (`Timings::request_timeout`) | `a_slow_composio_gives_up_at_the_limit_with_a_clear_error` |
| Hub, logo fetch | 10 s (`LogoCache::set_timeout`) | `a_logo_that_does_not_answer_gives_up_at_its_limit` |
| Worker, hub blob download | 60 s, or 30 s connect and 60 s read (`HttpLimits`) | `a_hub_that_never_answers_ends_a_blob_download_at_its_limit` |
| Worker, `git` (clone, ls-remote) | 2 min, clone 15 min (`git_with`) | `a_git_server_that_never_answers_ends_at_the_limit` |

## Details that the plan did not settle

- **Composio plan and usage.** Composio gives the plan and the usage only to a dashboard login (the billing endpoints are "cookie-auth only" in the OpenAPI file) or to a user key (`GET /auth/session/info`). A project key reaches neither. So `plan` and `limit` stay empty, and `usage.used` is the number of calls that the hub sent in the current month, counted from the audit log (`connector_calls`, outcome not `not_run`). `resets_at` is the start of the next month (UTC). The status is not stored with the usage. It is counted at each read.
- **A key that Composio refuses.** Every Composio client of the hub shares one flag. A `401` or `403` sets it, and any other answer clears it. `composio.status` shows the error at once. The hub also asks Composio at start, every hour, and when the last check is more than 10 minutes old, and it stores the result. A network failure changes nothing, because it says nothing about the key.
- **Connections of another project.** Composio has no project ID that the hub can compare. So the hub asks for each account after `composio.set_key` and at the hourly check. An account that Composio does not know (404) belongs to another project (or is gone). The connection becomes `needs_sign_in` with a message that names the cause. It stays in the list. When the old key comes back, the connections become `active` again.
- **Logos.** The hub URL is `<public url>/v1/logos/<sha256 of the origin>`. The route needs no login, because the client loads logos as plain images. The origin is registered when the hub learns it (a catalog read, a connection), so the route is not a proxy. Catalog keys live in memory. A connection also writes `<key>.url`, so its logo works after a restart. At start the hub gives old connections the current URL.
- **Private repos.** See the first decision row. Git runs in two setups. The clean one (no user config, no helper) is the default. The second one (the real home, the user's git config, the ssh agent) starts after an `https` server asked for a login, or at once for an ssh URL.
- **Branch.** A `#ref` after a repo URL is the one way to name a branch, a tag or a commit. A GitHub page URL (`/tree/<ref>/`) gives the same. A directory entry keeps it in its `repo_url`, and the installed skill keeps it in the `url` of its `directory` source. A marketplace `sha` wins over `ref`. A `ref` with a `/` in a GitHub page URL is ambiguous, so the page URL form takes only the first segment. Use `#feature/x` for such a branch.
- **`archive` and `npm`.** A plugin with one of these types lists its skills only when it names its `skills` folders (as for a plugin in another repo). The hub does not download a package to scan it. `npm` reads an exact version or a tag, because the hub has no semver resolver. A range is refused with the fix.
- **`command`.** See the decision rows. The entry stays in the list so that the user sees the plugin and the reason.
- **Expired login.** The case is the one that DECISIONS row 114 left open: `claude auth status` has no expiry, and `claude-agent-acp` reports a 401 as an internal error, not as `authRequired`. The detail is "The login expired. Sign in again." The app already reads an `error` state with "expired" in the detail as Expired (row 283), so the desktop needed no change.
- **OpenSSH.** Tested on macOS with OpenSSH 10.3 and LibreSSL 3.3.6. The test runs where `ssh` exists on Unix. Win32-OpenSSH is not tested.
- **Prune age.** 30 days since the last use, once a day, and at start. The age is a constant (`PRUNE_AGE`). A bundle in use by an open session never goes.

## What is left

- Win32-OpenSSH is not tested. The worker runs it for a workspace clone over ssh, as before.
- The `Plan` of Composio cannot be shown with a project key. A dashboard login or a user key would give it.
- The credential helper of a Windows hub (Git Credential Manager) was not tested. The environment keeps `USERPROFILE`, `APPDATA` and `LOCALAPPDATA` for it.
- An `npm` range (`^2.0.0`) is refused. A semver resolver would remove the limit.
- A plugin that lists no `skills` and has an `archive` or `npm` source gives no entry.
